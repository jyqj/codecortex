## 数量与 custody 的原文区别

`09-BENCHMARK.md` 第 7 节 D2 的表头是“规划覆盖（目标，不是已完成数量）”，题数写“初始约600个审阅问题”。因此不能仅凭这段规划新增“恰好或至少 600 题”的通用硬门。P8-002 的实际任务仍要求扩至规划语言/仓库覆盖并复核 gold。另一个已经冻结的 public-v19 preregistration 确实记录 `target_reviewed_families: 600`、六仓与 global-family 75/25 期望拆分；它是单独的冻结协议事实，本审计没有修改它。

原 04/06/09 要求无泄漏的 heldout 与独立 gold 复核，没有指定某家外部机构。实际阻断来自已有 custody 元数据：117 个 would-be holdout IDs 中至少 72 个已有曝光记录，checker 认证干净的数量为 0；访问主体、真实读取记录、首次可见时间与语义族关系仍未核验。该 checker 检查记录形状/状态，不等于认证真实访问控制。

本审计只读取原合同、台账、公开 DEV/compat 审计文档，以及旧协议的 `decision.json`、`CURRENT-DECISION.md`、`capability-evidence.json` 和 `preregistration.json` 元数据。没有读取 holdout 题目、gold 或其源码正文。完整 SHA256 与固定 anchor 在 JSON 中。

## 达到第 10 项所需的最小新增资源

沿当前全 local 路径，先真实完成前 7 项及 P8-002/003，第 10 项可以是 P8-004。它需要一个已有授权的非调参 custodian/evaluator 及可验证的访问边界，能出示主体/受众、调参者读取与导出隔离、管理权限、首次可见时间和读取历史。用户现有的独立执行者与环境只要能够证明这些事实即可。

新 heldout 必须来自未污染的独立任务族，固定源码 gold 经非调参者复核，并在候选/config/scorer 冻结后按预注册方案执行。结果按已有 custody 协议只返回允许的计数、哈希和汇总，正文继续保持隔离。共享工作目录、新文件名、chmod、保密指令或另一个同权限调参子代理都不能建立这种证据。

本报告不发起用户审批，也不以资源问题代替已经授权的工程工作。主代理应先完成当前固定源码实跑与可审查交付，再根据真实剩余阻断说明所需资源；没有执行的 task、延期决策或准备脚本不会被记为 done。
